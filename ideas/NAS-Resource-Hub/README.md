# NAS 资源订阅与自动下载中心

## 灵感卡

- **一句话想法**｜开发一个可独立安装在绿联 NAS 上的 Docker **影视资源发现与下载 Web 应用**：像视频网站一样展示有封面和简介的今日上新、电影和动漫/番剧清单，支持搜索；用户点击作品的下载按钮后，系统到已授权 PT（Private Tracker）站点检索候选种子，**由用户在多个版本中选择其中一个**，再将所选任务提交给保持运行的 qBittorrent Docker。
- **灵感起点**｜NAS 已安装 Docker，希望减少手动登录资源站点、逐个检查更新和手动下发下载任务的重复操作。
- **最想保留的点**｜**视频网站式的带封面和简介的可浏览清单与搜索体验**，以及「选择影视作品 → 系统自动查找 PT 资源 → 展示多个版本 → 用户选中一个 → 提交 qBittorrent 下载」的完整交互闭环；应用独立 Docker 化安装，不改变已有 qBittorrent 部署。
- **当前状态**｜灵感（AI-Workflow M0 目标探索入口；尚未批准调研、验证或开发）
- **下次打开时**｜讨论主页「今日上新」与搜索目录的数据来源，评估 Jellyfin 式元数据刮削方案及豆瓣、IMDb、TMDb 等来源的合法接口与封面/简介可用性；设计多版本种子列表（用户亲自选一个），再讨论通知规则。

## 当前用户体验主流程（2026-11-18 进一步确认）

1. 用户将本项目作为**独立 Docker** 安装至 NAS，通过浏览器进入其网页界面，风格类似视频网站，但**当前不要求在线播放影视内容**。
2. 首页有「今日上新」资源列表，可浏览电影、动漫／番剧等内容；支持关键词搜索作品名称。上新口径及海报/影视元数据来源待确认。
3. 用户选择感兴趣的影视作品并点击**下载**，无需先自行登录 PT 站手动寻找具体种子。
4. 系统在用户有权限访问、且允许相应自动化的 PT 站点中搜索作品资源，**以候选下载版本列表展示结果**；若存在十几种版本，用户可以浏览并明确选择其中一个。
5. **用户确认所选种子**后，系统才调用**已经保持运行的 qBittorrent Docker** WebUI API 创建该任务；网页可展示下发结果，后续可考虑任务进度。
6. 保留定时发现更新及邮件/其他通知作为原始诉求；是否支持「无需用户点击就自动下载」仍属待决范围，不与本次明确的「点选下载后自动查种/下发」混为一谈。

> 以上确认的是产品方向和主要交互链路，并非界面、数据源、自动匹配规则或开发计划全部获批。

## 已知环境与约束

- NAS：绿联 DXP4800；已安装 Docker。**新项目本身必须支持独立 Docker 容器化安装**，提供可浏览的 Web UI；本阶段仅接入现有 qBittorrent Docker。
- NAS 内存 8GB，无独显；优先轻量级服务，不安排本地 AI 推理。
- 磁盘空间相对充足，但后续仍需评估下载目录、容量告警、上传分享率和网络占用。
- 既有自有域名，但外网访问方式未确认；此创意没有提出必须公网开放管理页面。
- **资源来源已明确为 PT（Private Tracker）网站**，不是“PD”网站。具体站点、支持的 RSS/API 和自动化规则仍需逐站核验。
- 只监控用户有合法访问权的站点与内容；应遵守站点规则，不绕过认证、反自动化措施或分享率要求。
- 密码、Cookie、下载器凭据不得存入公开 GitHub 仓库；优先最小权限、密钥隔离、内部网络访问。
- 站点允许的订阅／自动化方式及个人数据、版权合规须在实施前确认。

## 2026-11-18 进一步澄清：独立 Docker 与多下载器兼容

### 用户已明确确认

- 资源站点类型为 **PT（Private Tracker）**。
- 目前 NAS 中 **qBittorrent 是一个 Docker 容器**；**迅雷和网盘工具是绿联系统内的原生 App**。
- 新 Idea 希望最终也成为**一个独立 Docker 容器**，可由用户自行安装；它需要协调已有下载工具，不应假设下载器与订阅中心安装在同一个容器内。
- 用户担心 Docker 与系统原生 App 之间存在技术对接困难；**2026-11-18 已明确选 A：只需自动创建下载任务，已有下载工具保持运行。**

### 已确认产品决策：A 方案（2026-11-18）

- **决策人**：项目所有者（用户）；**决定**：选择 A「主要是自动建立下载任务，下载工具保持运行」。
- **包含范围**：订阅中心 Docker 定时检测允许使用的 PT 更新来源，按规则通知并通过下载器现有 API 向已运行的客户端提交任务（自动化触发策略细节待定）。
- **排除范围**：不负责启动、停止、重启其他 Docker 容器或绿联原生下载 App；不需要为此申请 Docker 守护进程控制权限。
- **接入优先级**：优先接入已有 qBittorrent Docker 的 WebUI API；迅雷、网盘原生 App 作为未来可选适配，取决于是否存在安全、受支持的接口。
- **范围效力**：仅锁定这一项产品行为，**不代表 M0 整体获批，也不授权开发或部署**。后续要变更 A 方案需记录并重新征得用户确认。

### 初步可行性分析（仅技术预研结论，未在用户 NAS 上验证）

| 接入对象 | 可行性判断 | 证据与约束 |
| --- | --- | --- |
| qBittorrent Docker | 较高 | qBittorrent 提供官方 WebUI API，可添加 Torrent 和查询/管理任务；需确认实际版本、认证、可达性及容器网络设置。参考 [官方 qBittorrent WebUI API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-5.0))。 |
| UGOS Pro 原生迅雷 App | 待验证 | 绿联官方确认其 NAS 迅雷应用及远程下载能力，但尚未核实面向第三方的正式任务 API；不能将「App 有远程下载」等同「其他容器可以直接控制」。参考 [绿联官方应用列表](https://www.ugnas.com/support/download-list/id-27?id=27&product_type=nas&type=3)。 |
| UGOS Pro 网盘工具 App | 待验证 | 绿联官方确认网盘工具有同步/备份能力，但尚未核实通用第三方下载任务接口，且网盘同步与 PT 下载是不同场景。参考同一官方应用列表。 |
| Docker 容器启动/停止 | 技术上可能但安全敏感 | 真正管理其他容器需触及 Docker Engine 管理接口；不应默认挂载 `/var/run/docker.sock` 或将 Docker 管理端口暴露到网络。首版宜只经 qBittorrent WebUI API 提交下载任务。参考 [Docker 官方守护进程访问安全](https://docs.docker.com/engine/security/protect-access/)。 |

### 候选设计原则

1. **独立容器、适配层设计**：监控/规则/通知/任务调度放在本项目容器；下载通过可扩展的 `Downloader Adapter` 调用外部客户端。
2. **首版优先 qBittorrent**：先验证 PT 站点允许的更新接口与 qBittorrent API 全链路；迅雷、网盘 App 只作为后续可选适配，不作为首版成功的硬性依赖。
3. **已确认 A 方案**：本项目仅通过下载工具已支持的接口向正在运行的客户端添加、查询任务；**不负责启动/停止其他 Docker 容器或绿联原生 App**。不因本项目默认接入 Docker Engine 管理接口或挂载 Docker Socket。
4. **PT 专项边界**：每站点按其许可规则订阅、下载、做种与维持分享率；禁止默认把 PT 种子交给站点不认可的客户端，也不能因自动化造成密钥泄露或重复下载。
5. **保持既有安装不变**：用户现存 qBittorrent、迅雷、网盘 App 和下载数据原则上不迁移、不覆盖。

## 2026-11-18 · 最新产品定位及范围决定

### 正式确认的体验方向

- **产品定位调整**：从仅在后台定时监控的「订阅调度器」，扩大为具备影视目录、上新展示、分类搜索与一键下载能力的 **PT 资源发现 Web 应用**。
- **页面体验**：参考视频网站的内容发现体验，包括「今日上新」、电影、动漫/番剧与搜索入口；**所有展示的影视作品必须配有封面和必要简介**（已确认强制要求）。**当前不包含在线播放/转码**，具体元数据来源、图片授权、缺失补全机制待设计。
- **核心用户路径**：用户先搜索/浏览到**作品**，点击「下载」；应用自动检索该作品的**具体 PT 资源种子**并列出多个版本，**由用户手动选中其中一个**，才向保持运行的 qBittorrent Docker 提交任务。这是「作品」与「种子」两层不同实体。
- **后台功能**：保留原有定时发现 PT 更新、通知能力的需求方向；下载行为的已确认核心模式为「用户点击后自动查找并下发」，**并非已确认所有新资源都要无需点选地自动下载**。
- **下载引擎当前范围**：**只接入 qBittorrent Docker**。迅雷与网盘属于绿联原生 App，但**本阶段明确排除其接入、接口研究或相关开发**，除非用户未来重新决定。
- **运行策略沿用 A**：下载工具本身持续运行；本应用只创建/查询任务，不启动、停止或重启其他容器。
- **术语核对**：用户语音中「番茄」按上下文暂理解为「番剧」，细节以后可确认。

### 设计时必须拆开的两个问题

1. **作品目录如何生成**：今日上新可能指「PT 站新发布的种子（按电影聚合去重）」，也可能指「新上映/更新的影视作品」。两者不同；**电影一作品一条目已确认**，但上新定义、元数据来源和缓存机制仍待决定。
2. **多种子由用户选择**（已解决产品原则）：同一作品可能有不同季/集数、清晰度、字幕、发布组和体积。系统应把可辨别的候选种子及必要信息列出，让用户选中一个再下发；候选列表如何排序、去重、筛选和标注仍需设计。

## 2026-11-18 · 最新确认：用户选种 + 全作品封面与简介

### 决策 1：PT 多版本由用户选择

- **已批准交互规则**：作品页点击「下载」后，先在允许访问的 PT 站点检索种子，将候选版本显示给用户；**绝不默认从十几种版本中替用户选一个直接下载**。
- 用户可以明确选择其中一个候选项；确认后再向保持运行的 qBittorrent Docker 添加该种子。
- 候选列表建议展示：种子标题、所属站点、清晰度/视频规格、字幕/音轨、文件大小、发布时间及做种状态（仅作为待设计字段，须以各站真实可用资料为准）。
- 处理零结果、同名不同作品、季集数不匹配及重复下载的具体策略仍待设计。

### 决策 1A：一个电影作品只展示一个目录条目（2026-11-18 再次明确确认）

- **用户明确批准**：「同一套电影即使对应十几个 PT 种子，影视目录都只需要显示一个作品条目；进入下载选择时，先展示十几个可选版本」。
- **目录去重规则（电影）**：同一电影按规范化作品身份归为一个可浏览/可搜索的主条目，使用一份封面、简介等作品级元数据；不能因为 1080P、4K、不同发布组或多个 PT 站点就显示成十几张重复卡片。
- **下载选择规则**：一个电影主条目可以关联多个 PT 站、多个具体种子。用户进入选种界面后，才显示这些可选版本，由用户选一个提交 qBittorrent。
- **身份识别方向（待设计）**：可结合权威作品标识、中文/英文别名、上映年份进行消歧；如何处理重映、同名影片、合集、多部曲等场景仍需验证。
- **边界**：本次用户直接确认的是**电影**的聚合原则；电视剧、番剧的季/集结构及多种子展示规则留在 M0 后续确定，不能擅自等同电影。

### 决策 2：所有影视条目都必须带封面与必要简介

- **硬性产品要求**：任何面向用户展示的电影、剧集、动漫/番剧作品卡片或详情，**至少有对应封面图和可读的基本剧情简介**；不允许将缺失封面或空白简介作为合格成品。
- **候选来源**：参考 Jellyfin 的媒体元数据识别/刮削架构；用户提到豆瓣、IMDb，也可评估专门的合法元数据服务（如 TMDb、OMDb 等）。**尚未决定最终供应商、采集方式或授权方案**。
- **设计边界**：作品级影视元数据（封面、简介、年份、规范标题等）与 PT 种子级数据（大小、版本、发布组、做种情况）分开存储，通过作品标识与标题匹配关联。
- **需研究**：多来源优先级、中文简介优先、动漫元数据覆盖、名称/年份消歧、缓存与定期更新、资料接口条款和图片版权；若无法取得封面/简介，如何补录、纠错或暂不展示，仍需用户批准具体策略。
- **官方技术参考**：[Jellyfin 元数据来源](https://jellyfin.org/docs/general/server/metadata/)、[Jellyfin 元数据识别标识](https://jellyfin.org/docs/general/server/metadata/identifiers/)、[TMDb 图片接口](https://developer.themoviedb.org/reference/movie-images)。这些只用于可行性参考，不表示已选定依赖或获得商业/再分发授权。

## 2026-11-18 · 首页双区块正式决策（选项 C）

- **审批来源**：用户明确选择 C，并要求更新 IdeaLab、继续下一项 M0 需求设计。
- **首页区域一：PT 资源上新**。以用户有权访问的 PT 站点新增发布/更新的下载资源为依据；列表按影视作品聚合，**同一电影只显示一张带封面和简介的主卡**。发布时点与同步延迟需后续确定。
- **首页区域二：近期上映／更新**。以电影上映、剧集/番剧播出或更新等影视元数据为依据独立展示；与 PT 资源是否已经存在不是一回事。即使暂未找到可下载种子，也不应伪造可下载状态。具体时间窗口及影视信息来源待设计。

- **当前仅确认区域类型及语义**：默认排序、分页、资源同步频率、可下载状态、没有海报或简介时的处理、按季/集上新的展示，仍为开放问题。
- **既定范围不变**：继续只接入运行中的 qBittorrent；PT 多版本由用户选种；迅雷/网盘不在本阶段；无部署或开发授权。

## 2026-11-19 · 电视剧和番剧结构正式确认（方案 A）

- **决策来源**：用户明确选择 A：「作品 → 季 → 集结构，支持单集与整季资源选择」。
- **目录结构**：影视首页、搜索和分类中，同一电视剧/番剧以**一个作品主条目**出现，主条目有封面及基本简介。进入作品详情后按**季**展示，再展开**集**；不会因为更新一集就给整个目录新增一张独立作品卡。
- **下载入口**：
  1. 作品某一**集**可选择「下载本集」，应用检索与该集匹配的 PT 候选种子，用户选中某个版本后发送给 qBittorrent。
  2. 某一**季**可选择「下载整季」，应用检索该季对应的 PT 合集/季包种子，用户选中某个版本后发送给 qBittorrent。
  3. 若仅存在单集而不存在整季包，是否支持自动组合多个单集下载任务仍未决定；**不得默认为整季包存在**。
- **更新展示**：「近期上映／更新」可把某剧/番最近更新集数标示在原作品卡上，点击后进入季集详情。具体首页显示最新集数还是专门更新条目需后续交互确认。
- **资源数据边界**：电视剧/番剧的作品、季、集属于媒体目录；PT 单集或整季种子为可选下载资源，不与目录层级混成同一种实体。
- **已有决策继续有效**：两种首页上新区块 C、所有影视作品有封面与简介、同一电影一个作品卡、多 PT 版本由用户选一个、qBittorrent 常驻且是当前唯一下载引擎。
- **阶段边界**：本次为 M0 中的一项产品规则确认，不表示整体 M0 完成或批准设计、编码、部署。

### 下一项：影視资料自动刮削方案（候选，待用户选择）

- 建议采用「**作品元数据适配层 + 合法来源自动匹配 + 本地缓存 + 缺失补录**」思路，避免把 PT 种子信息直接当成作品简介或封面。
- **候选方案 A：多来源自动刮削（建议）**：按类型与语言优先从获得授权的元数据接口取资料，电影/剧集/番剧可有不同来源；缺失时依规则尝试其他来源，再进入待补录状态。可研究 TMDb、Bangumi 等，不在此时承诺所有资料都可覆盖。
- **候选方案 B：单一来源自动刮削**：优先降低配置和维护成本，但某些番剧或非主流作品可能缺失，仍须满足封面/简介硬要求。
- **候选方案 C：复用既有媒体库的元数据**：若用户另有 Jellyfin 等服务且愿意授权，可考虑读取其已整理的元数据；当前并未确认安装了 Jellyfin，也不应强制新部署。
- **验证要点**：中文内容优先及回退、作品 ID 和季集映射、封面/简介缺失后的处理、资料源条款、可达性、API 额度/认证与本地缓存策略。不能把「展示源有数据」当成已取得相应使用授权。
- **官方参考**：[Jellyfin 元数据提供者](https://jellyfin.org/docs/general/server/metadata/)、[TMDb API 常见问题与署名要求](https://developer.themoviedb.org/docs/faq)、[Bangumi API](https://github.com/bangumi/api)。本阶段只记录候选，不调用外部接口或抓取内容。
