## 角色、容量与恢复

| 角色/工作 | 执行与证据 | 不可替代的边界 |
| --- | --- | --- |
| Work 协调与编写 | 每个文章批次指定唯一写入上下文；维护来源、答复、修订、日志和提交。 | 未获 M4 授权不写正式正文；作者自查不是独立复核。 |
| 普通读者审查 | 每篇 5～10 个真实闭环，检查术语、业务原因、顺序、案例。 | 实际独立上下文和原始消息可追溯；不能以角色模拟冒充。 |
| SAP 配置顾问审查 | 每篇 5～10 个真实闭环，检查场景、配置、跨模块和账务。 | 实际系统、FPS/权限未验证须写清。 |
| SAP 开发人员审查 | 每篇 5～10 个真实闭环，检查事务、模型、接口和技术实现。 | 搜索索引、旧版与实机证据不能互相冒充。 |

按 99 × 3 × 5～10 估算 **1,485～2,970** 个有效闭环；一个闭环至少包含问题、答复、修订/不修订及复核四种实际事件，故原始事件量至少约 **5,940～11,880**，退回、补证、复验和恢复还会增加事件。此计算是容量规划，不代表耗时、预算、可用额度或已完成量；目前正式文章、审核闭环和运行过的审核数据校验器均为 0。

每批开始前记录实际可用的作者与三个独立审查上下文、模型/额度、责任文章、来源、预计会话容量和最小可恢复提交；未指定或额度不可用记为待分配，不能预先假定长期可用。分批大小由当时实际容量和文章复杂度决定，不承诺固定吞吐或后台继续；实测若不足、无法形成有效独立问题或角色不可用，暂停对应文章验收，记录原因。

记录文章版本 A、每轮原始消息与具体来源、答复、修订版本 B、同角色复核版本及时间；异常或重启后重新读取已提交事件，标记未完成与受版本变更影响的轮次，不重造问答。角色无法恢复时按项目规则标明新上下文并复读原材料；不能证明真实复验不计有效轮。10 轮后无论是已有还是新发现的阻断/严重缺陷，均须登记、修复并由独立角色复验，未解决不标通过，不虚构新增有效质询轮次。自动校验器只列为 M4 的拟实施准备事项，目前尚未实现或运行；最终还需对原文、角色独立性及证据做人工/独立复核。

M3 出口仍需完整逐篇证据判定、资源安排及独立评审；由所有者审批后才能进入 M4。M4→M5、最终 PR 验收和合并继续遵守既有人工决策，未获授权不执行生产 SAP 操作。
