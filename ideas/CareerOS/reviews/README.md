# CareerOS｜多角色审查与 Work 执行档案

此目录必须保留真实过程，不得事后编造讨论或冒充独立子代理。

## 目录约定
- `work/`：Work 执行日志、范围矩阵、研究证据、版本/模型/工具能力与决策
- `reader/`：普通用户/零基础读者的提问、理解障碍、Work 回答、修订与复验
- `consultant/`：资深 SAP 配置顾问的业务/配置/跨模块质疑、依据与复验
- `developer/`：普通 SAP 开发人员的 T-Code、表、接口、调试与实现质疑、依据与复验
- `summary/`：缺陷汇总、回合统计、交叉争议、最终验收报告

## 每个角色每篇文章按需 5～10 轮
「一轮」必须包含：角色提出**实质性且不同**的问题或批评 → Work 有依据地回答 → Work 评估是否修改并记录差异 → 角色复核回答和修订结论。未完成四步不计轮次；单纯重复、空泛赞美或拆分同一问题凑数不计入。每个角色每篇正式文章按需进行 5～10 个有效轮次，三角色合计 15～30 轮；不同文章不得复用回合数。

每轮记录：`article_id`、`role`、`round`、`question`、`evidence`、`work_response`、`change_ref`、`recheck`、`status`、`executor_context`、`timestamp`。可使用 Markdown 或 JSONL；摘要需可追溯至原文与 Git commit。

三角色必须按自身视角独立提出问题：
- 普通用户：看不看得懂、为什么做、术语是否解释、业务故事是否完整。
- 资深 SAP 配置顾问：配置条件、组织结构、跨模块差异、会计与税务前提、版本适用性。
- 普通 SAP 开发人员：T-Code、数据模型、增强点、接口、调试、技术可验证性。

Work 是协调/写作/答辩角色，不可将 Work 自问自答伪装成三个独立代理。若环境不支持真实独立代理，应如实标注“同一上下文角色模拟”，并记录独立性缺口；不得声称完成独立审查。5 轮是每个角色的最低数，具体按复杂度、风险和问题数量选择至多 10 轮；轮数不代表质量自动达标。10 轮后仍有阻断或严重问题时，保持未通过，记录问题和需要的处理；如确需超过本次约定范围，先提交说明并取得所有者决定。

阻断性错误必须修正并重新复核；未验证的 SAP 事实须标记，不能伪称已在系统中测试。不得写入企业机密。
